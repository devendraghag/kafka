D1

Start with the problem

A person reports a lost item. The system should accept the report and make it available as an event that another part of the system can read.

Need 1: accept a report

Receive itemId and description through POST /lost-items and reject blank required fields.

Need 2: give it an identity

Create an eventId and a timestamp so the report event can be recognized later.

Need 3: store and hand it off

Publish the report to Kafka so a consumer can read it separately from the HTTP request.

Need 4: see what happened

Log the Kafka key, topic, partition, offset, timestamp, and event value.

Learning goals and limits

The design is small on purpose: one broker, one topic partition, one producer, and one audit consumer. It teaches the message path. It does not yet provide search, a business database, email/SMS, multi-broker failover, authentication, or a production dashboard.

D2

A simple analogy: a lost-property desk

Imagine a front desk, an archive room, and an auditor who checks the archive later.

API = front desk

A person reports a wallet. The clerk checks the form and prepares a report.

Topic = labeled notebook shelf

Reports go into the notebook named lost-found.events.

Partition = one ordered notebook

New reports are appended. Each page position is like an offset. This project has one notebook.

Key = filing label

The item ID labels a report. With many notebooks, it helps keep the same item's reports together.

Consumer = auditor

The auditor reads the notebook independently and writes what they saw into a log.

Retention = archive cleanup rule

Old notebook sections can be removed according to policy. Cleanup happens in the background.

Where the analogy stops: an offset is only a position inside one partition. To find a record, pair its partition number with its offset. Offset 5 in partition 0 is a different position from offset 5 in partition 1.
D3

System design at a glance

There are two paths: the request path that writes an event, and the consumer path that reads it later.

Main design idea: the API does not call the audit method directly. It writes an event to Kafka. The consumer reads that event independently. Kafka is the handoff point and durable log between those two jobs.
Write path

Caller ? API ? producer ? broker ? topic partition. The API waits for Kafka's acknowledgment before returning.

Read path

Topic partition ? consumer group ? audit listener ? application log. The listener handles records asynchronously.

D4

Component boundaries: who owns each job?

A component should have one clear responsibility. It sends information to the next component through a defined connection.

ComponentOwns this jobConnection to the next part
CallerSupplies itemId and description.Sends HTTP JSON to the Spring endpoint.
REST controllerValidates input and creates the business event.Calls the producer with the event.
ProducerChooses the topic and Kafka key, then sends.Sends key and serialized value to the broker.
Kafka brokerStores records in topic partitions and serves readers.Consumer fetches records from the topic.
Audit consumerReads the event and writes diagnostic information to the app log.Listener receives a decoded ConsumerRecord.

In this project the controller, producer, and consumer are Java components in one Spring Boot application. Kafka is a separate service in Docker. In later designs, the producer and consumer roles could run in separate services without changing the topic contract.

When you report an item, the producer sends a record to the broker. It says which topic to use, provides the key (itemId) and the event data. Kafka puts the record in one of that topic's partitions and assigns it an offset. The consumer later reads the record from the broker.

For this project, there is one broker, one topic, and one partition. So every report goes into partition 0, regardless of its key. The key becomes useful when a topic has multiple partitions: Kafka uses it to choose a partition, helping keep events for the same item together.

An offset is not the report's eventId. The app creates eventId to identify the report; Kafka assigns an offset to identify its position in a partition. To locate a Kafka record, use partition + offset.

Then follow the code flow

  1. docker compose up -d starts the broker: the Kafka server.
  2. The Kafka CLI creates the topic lost-found.events on that broker. The topic is the named stream; it has one partition, an ordered log numbered 0.
  3. POST /lost-items reaches LostItemController.report. It creates an ItemReportedLost event with an application-generated eventId and timestamp.
  4. The controller calls ItemEventProducer.publish, which calls KafkaTemplate.send(topic, event.itemId(), event). That sends the topic, the key (itemId, such as wallet-42), and the event value.
  5. Kafka serializes the key and event value, then stores the record in the topic's partition. Since this topic has only one partition, every record goes to partition 0. Kafka assigns an offset to each record in that partition.
  6. After Kafka acknowledges the send, the controller returns HTTP 202.
  7. Spring's consumer reads the record and calls ItemAuditConsumer.audit. It logs the key, topic, partition, offset, Kafka timestamp, and event.

So: the broker is the server; the topic is the named stream hosted by Kafka; the partition is the ordered log inside that topic; and the record is an entry in that log. The app's eventId identifies the report. Kafka's partition and offset identify where the record is stored.

3

Trace the request through the code

Read these files in this order to see how one HTTP request turns into a Kafka record.

  1. HTTP endpoint - LostItemController.java
    Maps POST /lost-items. Validates that itemId and description are not blank. It creates a UUID event ID and current timestamp, then waits up to ten seconds for Kafka's send result before returning HTTP 202.
  2. Event data - ItemReportedLost.java
    A Java record describing the event. The event ID identifies this occurrence in the application. It is separate from Kafka's offset.
  3. Producer - ItemEventProducer.java
    Calls KafkaTemplate.send(topic, key, value). Here, topic is lost-found.events, the key is itemId, and the value is the event object.
  4. Serialization and connection - application.yml
    Configures JSON for the event value, string serialization for the key, and the broker address. On the consumer side it configures JSON deserialization and a consumer group. acks: all asks the broker to acknowledge the send after all current in-sync replicas have it; in our one-replica topic, that is the one replica.
  5. Audit listener - ItemAuditConsumer.java
    @KafkaListener subscribes to the topic. The method receives a Kafka ConsumerRecord and logs the key, topic, partition, offset, broker timestamp, and event body.
Two timestamps: the event's timestamp is set by the application before send. kafkaTimestamp in the audit log is metadata attached to the Kafka record. They describe related times but are distinct values.
D7

Why this architecture? What are the trade-offs?

Every design choice solves one problem and may leave another problem for a later phase.

Kafka between API and audit

Benefit: the writer and reader do not call each other directly. Kafka keeps the event until a consumer reads it, subject to retention.

itemId as the key

Benefit: events about the same item can stay in one partition when the topic grows. In this one-partition project, every item still lands in partition 0.

One partition

Benefit: simple to inspect and records have one clear order. Cost: no parallelism across partitions, and no per-item distribution lesson yet.

One broker and replication factor one

Benefit: easy local setup. Cost: no copy on another broker if this broker fails. acks=all cannot create a missing replica.

Wait for producer acknowledgment

Benefit: the HTTP handler knows the send succeeded before responding. Cost: the HTTP request depends on Kafka being reachable and can wait up to the configured timeout.

Audit log as the consumer action

Benefit: easy to see what was read. Cost: logs are for learning and diagnosis; this is not a permanent notification database.

System design boundary: Kafka stores this event, but this phase has no database for current item status, no deduplication key on the HTTP request, and no retry or dead-letter flow. Those are later reliability topics.

Create the topic

A topic is divided into partitions. We create one partition and one replica because this is a single-broker learning setup.

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic lost-found.events --partitions 1 --replication-factor 1 --config retention.ms=604800000

--if-not-exists makes this safe to run again. retention.ms=604800000 sets seven days in milliseconds. The dot in the topic name may produce a metric-name warning; Kafka still accepts the topic.

Describe it

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic lost-found.events

Look for PartitionCount: 1, partition 0, a leader, and one replica. Since there is only one broker, the leader and replica are on that broker. This setup is for learning, not broker-failure protection.

Inspect the stored record

Kafka's command-line consumer can read the same topic independently of your Spring listener.

Read records from the beginning

docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic lost-found.events --from-beginning --property print.key=true --property print.partition=true --property print.offset=true --property print.timestamp=true

Stop the command with Ctrl+C. It prints prior records and then waits for new ones. --from-beginning is for this console consumer; it does not reset the Spring listener's saved group offset.

Read one partition position

Offsets start at zero in each partition and increase as records are appended. If the audit output showed partition 0 and offset 3, you can ask Kafka to read from that position:

docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic lost-found.events --partition 0 --offset 3 --max-messages 1 --property print.key=true --property print.partition=true --property print.offset=true

Replace 3 with the offset you want. If the record has expired or that offset does not exist, the command may return no record.

ValueWho assigns it?What it tells you
eventIdSpring app (UUID)Which business event this is
itemIdRequest callerWhich item is reported; used as Kafka key
partitionKafkaWhich partition contains the record; here always 0
offsetKafkaRecord position within that partition; not globally unique across partitions
Key intuition: with only one partition, every item goes to partition 0, so the key does not visibly distribute data. With multiple partitions, Kafka's key-based partitioner maps the same key consistently to a partition. That helps keep events for the same item in order within that topic partition.
CLI

Kafka commands, explained piece by piece

All six commands run Kafka's command-line tools inside the running kafka container. Read them as: enter the container, connect to the broker, then ask Kafka to do one specific job.

Common beginning: docker compose exec kafka means "run a command inside the already-running service named kafka." The tool after it, such as kafka-topics.sh, is included in the Kafka container image. --bootstrap-server localhost:9092 tells the tool where to make its first Kafka connection. Here the command runs inside the broker container, where Kafka listens on port 9092.

1. Create the topic

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --if-not-exists --topic lost-found.events --partitions 1 --replication-factor 1 --config retention.ms=604800000
PartMeaning

2. Describe the topic

docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic lost-found.events

--describe asks Kafka to report the topic layout; --topic selects which topic. Look for a partition count of 1, partition 0, and fields named Leader, Replicas, and Isr (in-sync replicas). With one broker and replication factor one, all three refer to that broker. This command inspects configuration and placement; it does not read event values.

3. Read records from the beginning and print metadata

docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic lost-found.events --from-beginning --property print.key=true --property print.partition=true --property print.offset=true --property print.timestamp=true

kafka-console-consumer.shStarts a command-line consumer that prints record values.

4. Read one record from partition 0, offset 3

docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic lost-found.events --partition 0 --offset 3 --max-messages 1 --property print.key=true --property print.partition=true --property print.offset=true

--partition 0 chooses the partition. --offset 3 starts reading at offset 3 (offsets begin at 0). --max-messages 1 stops after one record, making this a focused lookup. Replace 3 with the offset seen in your app log. If that position is beyond the current end, or the record is no longer retained, you may get no record. An offset identifies a position, not an eventId.

5. Temporarily set retention to five seconds

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 --entity-type topics --entity-name lost-found.events --alter --add-config retention.ms=5000

kafka-configs.sh edits Kafka configuration. --entity-type topics says the target is a topic; --entity-name lost-found.events names it; --alter changes its settings; --add-config retention.ms=5000 sets the retention value to 5,000 milliseconds, or 5 seconds.

Five seconds is not an exact deletion countdown. Kafka removes eligible log segments in the background. A record can remain visible after five seconds because a segment may not yet be eligible or cleanup may not have run. Send a fresh record, wait, and inspect again to learn the behavior; do not expect an exact delete time.

6. Restore seven-day retention

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 --entity-type topics --entity-name lost-found.events --alter --add-config retention.ms=604800000

This uses the same configuration command as step 5, but changes the value back to 604,800,000 ms (7 days). Kafka will apply the restored policy as log cleanup runs. If you skip this step, the five-second setting remains on the topic.

Suggested order

Create the topic once; describe it; publish a report; use command 3 to read records; copy a partition and offset from the output; use command 4 to read that position; then try commands 5 and 6 for retention. This connects topic setup, stored record metadata, and topic lifecycle.

Experiment with retention

Retention controls how long Kafka keeps log data. It is not a timer attached to each event.

Temporarily use five seconds

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 --entity-type topics --entity-name lost-found.events --alter --add-config retention.ms=5000
  1. Run the config command above.
  2. Submit a new lost-item report and note its partition/offset.
  3. Wait, then inspect the topic or read that offset again.
  4. Observe that cleanup can take longer than five seconds.
Why it may still be there: Kafka deletes old log segments in the background. A segment can contain several records, so Kafka generally removes eligible segments as a unit. With the default segment size and rolling settings, a short retention period is not a precise five-second deletion stopwatch. The experiment teaches eventual expiration; exact timing depends on segment rolling and cleanup.

Restore seven days

docker compose exec kafka /opt/kafka/bin/kafka-configs.sh --bootstrap-server localhost:9092 --entity-type topics --entity-name lost-found.events --alter --add-config retention.ms=604800000

Interview answer: explain this project in one minute

Use this as a speaking guide. Learn the flow, then say it in your own words.

Sample answer
This project is a small event-driven Lost and Found system. A caller sends a lost-item report to a Spring Boot REST API. The controller validates it and creates an ItemReportedLost event with a unique eventId and timestamp. A producer sends the event as JSON to the lost-found.events Kafka topic, using itemId as the record key. Kafka stores it in partition 0 and assigns an offset. An audit consumer in its own consumer group reads the record and logs the key, topic, partition, offset, Kafka timestamp, and event. The API waits for Kafka to acknowledge the publish before it returns HTTP 202. This shows the producer, consumer, topic, key, partition, offset, and JSON flow. The setup uses one broker and one replica, so it is for learning and does not provide broker failover.
Tip: explain the path first, then mention one trade-off.

Walk the interviewer through the architecture picture

  1. Start at the caller: it sends itemId and description over HTTP.
  2. Move to the Spring controller: it validates the request and creates the event object.
  3. Follow the write arrow: the producer sets itemId as key, serializes the event to JSON, and sends it.
  4. At Kafka: the broker appends the record to the topic partition and assigns metadata.
  5. Follow the read arrow: the audit consumer fetches, deserializes, and logs the record.
  6. Finish with the response: the controller returns after the broker acknowledges the send.
Simple interview pattern: problem -> components -> event path -> one design choice -> one limitation. This keeps your explanation clear and accurate.
Q&A

Common interview follow-up questions

Open a question, learn the simple answer, then practice saying it without reading.

Why put Kafka between the API and the audit consumer?

It separates the writer from the reader. The API publishes an event, and the consumer can read it when ready. Kafka also keeps a log that can be read again. In this small project we have one consumer; later, different consumer groups can use the same event for different jobs.

Why use itemId as the Kafka key?

Events about the same item should normally go to the same partition. Kafka uses the key to choose a partition. This topic has one partition, so every event goes to partition 0. The key choice becomes useful when the topic has multiple partitions.

What is the difference between eventId and offset?

eventId is created by the application to identify the business event. Offset is assigned by Kafka to show a record position inside one partition. A Kafka location needs partition plus offset. They solve different problems.

How are consumer groups different from topics?

A topic is the shared event log. A consumer group is a reader identity with its own progress through that log. Consumers in one group share partitions. Two different groups can each read the same topic independently.

What ordering does this project provide?

A Kafka partition is ordered. Since this topic has one partition, all records have one order. If we add partitions, ordering is guaranteed within each partition, not across the whole topic. Using itemId as key keeps an item's events together under the normal key partitioner.

What does acks=all guarantee here?

The producer waits for all current in-sync replicas to acknowledge the write. The topic has replication factor one, so there is only one replica. This setting does not protect the event if that single broker is lost.

Does HTTP 202 mean the consumer finished its work?

No. In this implementation the controller waits for the Kafka send acknowledgment, then returns 202. The audit consumer is a separate asynchronous reader. The HTTP response confirms the publish completed, not that every consumer completed future business work.

What happens if the audit consumer is temporarily down?

Kafka retains the records according to the topic retention policy. When the consumer returns, its group normally continues from its last committed position. If the group has no saved position, this project uses earliest as the starting point. Retention can eventually remove old records.

Is this exactly-once processing?

No. The project demonstrates producing and consuming, not an end-to-end exactly-once business transaction. The database/idempotency/retry work belongs in later phases. Be precise: a Kafka producer acknowledgment is not proof that an external business action happened exactly once.

How would you scale this design?

Add topic partitions and more brokers, then run more consumers in the same group. Kafka assigns partitions among group members. A group cannot actively use more consumers than the topic has partitions. Keep itemId as the key so the same item's events stay in one partition.

What would you improve before production?

Use multiple brokers and replicated partitions, define min.insync.replicas, add bounded retry and a dead-letter topic, make downstream work idempotent, add schema management, secure Kafka, and monitor lag and broker health. The right order depends on business needs.

Why is the event JSON and what is serialization?

The Java event is an object in the app. Kafka transports bytes. A serializer converts the object to JSON bytes before send; a deserializer rebuilds the Java object for the listener. Both sides must agree on the format and fields.

P2

Consumer groups: fan-out versus work sharing

Think of Kafka as a notice board with three separate teams: audit, email, and SMS. Each team can read the same event and keeps its own reading progress.

Fan-out: separate teams

audit-group, email-group, and sms-group each read the same Kafka event independently. Reading it in one group does not stop the other groups from reading it.

Work sharing: two people on one team

If two email app instances use the same email-group, Kafka divides the partitions between them. Each partition is assigned to one instance at a time, so they share the email work.

Start a second email instance

An instance means one running copy of the app. Leave the main app running, open a second PowerShell window in the project folder, and run:

$env:EMAIL_CONSUMER_ENABLED = 'true'
$env:SMS_CONSUMER_ENABLED = 'false'
$env:AUDIT_CONSUMER_ENABLED = 'false'
$env:KAFKA_CLIENT_ID = 'email-instance-2'
.\mvnw.cmd spring-boot:run '-Dspring-boot.run.arguments=--server.port=8082'

This starts the second copy on port 8082 with only its email consumer enabled. It joins the same email-group as the main app. Kafka shares the email group's partitions between the two instances. The SMS and audit groups continue reading independently.

Check group members and partition assignments

Remember: separate groups each get to read the event. Multiple instances in the same group divide that group's partitions and work.

Avro and Schema Registry: the event contract

Avro schemas define the fields and data types of Kafka events. Schema Registry stores versions and checks compatibility as the event format evolves.

How they work together: the producer uses Avro to encode an event and registers or looks up its schema in Schema Registry. The event carries a schema ID, so consumers can find the right schema and decode the event.
Avro schema file

src/main/avro/ItemFound.avsc describes the fields in an item-found event. Maven uses the Avro file to generate the Java ItemFound class.

Schema Registry service

Docker Compose starts Schema Registry, and src/main/resources/application.yml configures the app to connect to it. The Avro serializer and deserializer use Registry when producing and reading events.

Producer side

KafkaTemplate hands the Avro record to KafkaAvroSerializer. It contacts Registry and encodes the record with a schema ID.

Consumer side

KafkaAvroDeserializer reads the schema ID, retrieves the schema as needed, and reconstructs a typed event for the listener.

Order matters: publish V1 first, then V2, against a fresh ItemReportedLost subject. V2 adds an optional field, so a new reader can read old data. If Registry already has V2, registering the older V1 schema may be rejected by backward compatibility. The Project 1 console consumer expects JSON; it will not show Avro values as readable JSON.

ItemFound has its own schema. Its itemId key matches the lost event, so Kafka routes both to the same partition and that partition preserves their publish order.

Interview answer: explain Projects 1 and 2 together

Explain the Project 1 producer and audit consumer first, then describe the readers, found-item event, partitions, and Avro schemas added in Project 2.

Sample answer
Project 1 builds a Spring Boot endpoint that creates a lost-item event and publishes it to Kafka using itemId as the key. Kafka stores the record in a partition, assigns an offset, and an audit consumer reads it. Project 2 adds email and SMS consumer groups. Because their group IDs differ, each group receives its own copy of every event. Two email instances in the same group share partitions, and Kafka rebalances assignments when an instance joins or leaves. The topic has three partitions, and the itemId key keeps one item's events together so ItemReportedLost and ItemFound retain their order in that partition. Event values use Avro, and Schema Registry stores schema versions. We add reportedLocation as an optional field with a null default so a new reader can handle older events. Email and SMS are simulated in logs; they are not sent to real providers.

P3

Project 3: Reliable notification delivery

Project 3 makes the email consumer safer when delivery fails or Kafka redelivers an event. It adds bounded retries, a dead-letter topic, a duplicate-safe database job, controlled offset acknowledgements, producer idempotence, and an optional Kafka transaction exercise.

What this demo guarantees: the email side effect is simulated and stored as one PostgreSQL job per event and channel. Kafka may deliver a record again, so the database write is idempotent. Kafka transactions cover Kafka records and Kafka offsets; they do not include the PostgreSQL database or a real email provider.
1. Retry, then send to the DLT

A temporary failure is retried twice after the first attempt, with a 500 ms pause. A permanent failure goes to email.notifications.DLT with the original event and exception metadata.

2. Make database work idempotent

notification_jobs has a unique constraint on (event_id, channel). Reprocessing the same event cannot create a second email job.

3. Acknowledge after successful work

Record mode lets Spring commit after the listener succeeds. Manual immediate mode explicitly acknowledges after the database processor returns.

4. Know the guarantee boundaries

Producer idempotence handles Kafka producer retries. Kafka transactions can atomically write to multiple Kafka topics and commit consumed offsets, but cannot atomically include PostgreSQL.

Start Kafka, Schema Registry, and PostgreSQL

docker compose up -d
.\mvnw.cmd spring-boot:run

Project 3 uses the three-partition topic from Project 2. The app creates the email DLT and transaction output topics. Compose starts PostgreSQL and the app creates notification_jobs from src/main/resources/schema.sql.

1. Retry once, then succeed

Put [FAIL_ONCE] in a lost-item description. The email consumer throws on its first attempt, waits, retries, and then writes one completed job. SMS and audit continue independently.

Invoke-RestMethod -Method Post -Uri http://localhost:8080/lost-items -ContentType 'application/json' -Body '{"itemId":"wallet-retry","description":"Wallet [FAIL_ONCE]"}'

2. Fail every attempt, inspect the DLT, then continue

Use [FAIL_ALWAYS] to make all three attempts fail. The error handler publishes the failed event and exception metadata to the DLT. A later valid event should still be processed.

Invoke-RestMethod -Method Post -Uri http://localhost:8080/lost-items -ContentType 'application/json' -Body '{"itemId":"wallet-dead","description":"Wallet [FAIL_ALWAYS]"}'
Invoke-RestMethod -Method Post -Uri http://localhost:8080/lost-items -ContentType 'application/json' -Body '{"itemId":"wallet-ok","description":"Valid later event"}'

Enable the DLT inspector on a second app process to log the failed Avro value and error headers:

$env:EMAIL_CONSUMER_ENABLED = 'false'
$env:SMS_CONSUMER_ENABLED = 'false'
$env:AUDIT_CONSUMER_ENABLED = 'false'
$env:EMAIL_DLT_INSPECTOR_ENABLED = 'true'
$env:KAFKA_CLIENT_ID = 'dlt-inspector'
.\mvnw.cmd spring-boot:run '-Dspring-boot.run.arguments=--server.port=8082'

3. Inspect the duplicate-safe database job

The database row is committed before the listener returns. Its unique event and channel key makes a redelivery safe.

docker compose exec postgres psql -U lost_found -d lost_found -c "SELECT event_id, channel, item_id, status, attempt_count FROM notification_jobs ORDER BY id DESC LIMIT 10;"

4. Simulate the database/offset crash window

Put [CRASH_AFTER_DB_COMMIT] in a description. The demo inserts the job, then throws before the listener acknowledges the offset. Kafka retries the event; the unique constraint prevents a duplicate job, and the repeated database operation is recognized as already done.

Invoke-RestMethod -Method Post -Uri http://localhost:8080/lost-items -ContentType 'application/json' -Body '{"itemId":"wallet-crash","description":"Wallet [CRASH_AFTER_DB_COMMIT]"}'

5. Compare record and manual acknowledgements

enable.auto.commit is disabled. With the default record mode, Spring commits after the listener returns successfully. To try explicit acknowledgement after database work, stop the app and restart it in manual immediate mode:

$env:KAFKA_ACK_MODE = 'manual_immediate'
.\mvnw.cmd spring-boot:run

Both modes are at-least-once: a record can be delivered more than once. That is why the database consumer must be idempotent.

6. Producer idempotence and Kafka transactions

The producer uses acks=all, retries, and enable.idempotence=true. This prevents duplicate Kafka appends caused by producer retries within a producer session; it does not deduplicate two separate HTTP submissions.

The separate transaction listener is disabled by default. Enable it before starting the app:

$env:KAFKA_TRANSACTION_DEMO_ENABLED = 'true'
.\mvnw.cmd spring-boot:run

It consumes from lost-found.events, publishes each event to notification.transactional.audit and notification.transactional.email, and commits the source offset in the same Kafka transaction. Include [TX_ABORT_ONCE] in the description to abort the first attempt; redelivery then succeeds. Read the output topics with committed isolation:

docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic notification.transactional.audit --from-beginning --isolation-level read_committed --max-messages 1 --property print.key=true
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic notification.transactional.email --from-beginning --isolation-level read_committed --max-messages 1 --property print.key=true

Both committed output records become visible together. Kafka transactions do not include PostgreSQL.
